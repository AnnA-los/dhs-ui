# 项目踩坑复盘与高频问题手册

这份文档专门给后续开发会话/模型使用。目标不是重复架构说明，而是把项目里已经反复踩过、最容易被误改的问题写成“现象 -> 根因 -> 解决方案 -> 避免方式”。

## 1. 登录后不能直接认为 token 已经代表最终业务身份

现象：

- 普通登录接口成功，但进入业务页后数据为空、医院不对或接口权限异常。
- 登录流程里出现“选择医院”弹窗，选择后才正常。

根因：

- `/login` 返回的 token 可能只是临时登录态。
- 如果响应里有 `needSelectHospital`，必须再调用 `/medical/hospital/select-login/{hospitalUserId}`。
- 第二个接口返回的新 token 才包含当前医院上下文。

解决方案：

- 保持 `src/views/login.vue` 中的医院选择流程。
- 选择医院成功后必须 `setToken(response.token)` 并 `commit('SET_TOKEN', response.token)`。
- 后续医疗接口统一走 `src/utils/request.js`，让 token 自动带上。

避免方式：

- 新增登录相关能力时，先检查是否影响 `needSelectHospital` 分支。
- 不要把医院选择弹窗当成普通 UI 可选项删掉。
- 不要在业务页面自行保存 hospitalId 替代 token 上下文。

## 2. 切换医院后必须整页刷新

现象：

- 切换医院后菜单、列表、下拉选项还是旧医院数据。
- 新医院下操作了旧医院的病历、收费、库存。

根因：

- 当前医院上下文存在于后端 token/session，也残留在前端 Vuex、keep-alive、tagsView、页面 data、远程下拉 options 中。
- 仅局部刷新一个接口不足以清理所有旧状态。

解决方案：

- 保留 `src/layout/components/Navbar.vue` 中 `switchHospital()` 成功后的 `window.location.reload()`。

避免方式：

- 不要为了“体验更顺滑”把整页刷新改成局部刷新。
- 如确实要优化，必须同步清空 Vuex 用户/权限/路由、tagsView、dict/options、所有 keep-alive 页面状态，并重新拉菜单，成本很高。

## 3. 前端看不到完整业务路由，不代表页面无用

现象：

- 在 `src/router/index.js` 没找到某业务菜单，以为页面废弃。
- 改了 `src/views` 路径后菜单白屏。

根因：

- 主业务菜单由后端 `/getRouters` 下发。
- 前端 `src/router/index.js` 只保留公共路由、少数隐藏路由和补充动态路由。
- 后端返回的 `component` 字符串会动态映射到 `src/views/${component}`。

解决方案：

- 改页面路径、文件名、路由 name 前，必须确认后端菜单配置。
- 新增菜单页时，前后端同步 component 路径。

避免方式：

- 搜路由时同时看 `src/store/modules/permission.js`。
- 不要只凭前端 router 文件判断业务入口。

## 4. `/medical/visitUsage` 是隐藏关键页，不能删

现象：

- 接诊病历点“收费明细”跳转失败。
- 收费明细页打开后没有数据或无法新增。

根因：

- 收费明细页是前端隐藏路由，定义在 `src/router/index.js` 的 `constantRoutes`。
- 它依赖 query 参数 `visitId`，不是独立菜单页。

解决方案：

- 从病历页跳转必须带：`/medical/visitUsage?visitId=<visitId>`。
- 保留路由 meta 的 `activeMenu: '/medical/visit'`，让侧边菜单高亮病历菜单。

避免方式：

- 不要把它从 `constantRoutes` 删除。
- 不要改成必须从后端菜单下发，否则病历页内部跳转会受菜单权限配置影响。

## 5. 日期清空后恢复当前月不是 bug

现象：

- 用户清空日期范围，页面又自动回到本月。
- 模型容易误以为这是交互 bug，改成空范围查询。

根因：

- 多数列表和报表默认当前自然月，用于防止误查全量数据、减轻后端压力，也符合经营数据默认看本月的业务习惯。
- 通用方法是 `restoreCurrentMonthRange(value, withTime)`。

解决方案：

- 预约、病历、收费、排班、随访、报表等页面继续使用当前月默认范围。
- 若业务明确要求支持全量查询，必须同时评估后端索引、分页、权限隔离和接口性能。

避免方式：

- 不要把清空日期自动恢复当前月当成普通表单问题处理。
- 新增经营类列表时优先沿用 `getCurrentMonthRange()` 或 `getCurrentMonthTimeRange()`。

## 6. 预约跳病历依赖后端菜单标题查找

现象：

- “新增病历”跳转路径看起来奇怪：先按标题找菜单，找不到才回退 `/medicalPatient/visit`。

根因：

- 业务菜单路径由后端配置，历史上路径可能变化。
- `src/views/medical/appointment/index.vue` 用 `findMenuPath(..., '接诊病历')` 兼容菜单路径变更。

解决方案：

- 保留按菜单标题查找真实路径的逻辑。
- 如果后端菜单标题改名，必须同步这里，或改成更稳定的菜单标识。

避免方式：

- 不要直接硬编码成当前环境看起来正确的路径，除非确认所有环境后端菜单一致。

## 7. 编辑预约时医生下拉要合并历史医生

现象：

- 编辑老预约时医生字段空了。
- 保存后医生被清掉或校验失败。

根因：

- 医生下拉按部门和关键词远程筛选。
- 历史医生可能已离职、换部门、停用，无法从当前 options 返回。
- 代码用 `currentDoctorOption()` 和 `mergeDoctorOptions()` 保留当前医生回显。

解决方案：

- 编辑预约时先把当前医生放入选项，再合并远程查询结果。
- 新增类似远程下拉时也要处理历史值回显。

避免方式：

- 不要在编辑页只使用接口返回的当前筛选 options。
- 不要在部门变更/远程搜索时无条件清空已有合法历史值。

## 8. 编辑收费明细时库存可用量要加回原用量

现象：

- 编辑已有药品/耗材明细，数量明明没变也提示库存不足或无法保存。

根因：

- 新增时可用库存是当前剩余数量。
- 编辑时原明细已经占用了库存，如果只看当前剩余数量，会把自己的已用数量也算成不可用。
- 代码中使用 `availableQuantity + usedQuantity` 作为编辑时最大可用量。

解决方案：

- 保留 `src/views/medical/visitUsage/index.vue` 中编辑时的 `currentAvailable = availableQuantity + usedQuantity`。

避免方式：

- 凡是编辑“已占用库存”的记录，都要把当前记录原占用量加回可用范围。
- 不要简单复用新增表单的库存限制逻辑。

## 9. 收费明细里的项目/加工定制只选可售数据

现象：

- 用户能把停售项目、非收费加工项加入收费明细。

根因：

- 收费明细 options 对项目和加工定制有业务过滤：
  - 项目：`saleStatus: '0'`
  - 加工定制：`sourceType: 'CHARGE'`、`saleStatus: '0'`

解决方案：

- 保留 `remoteItems()` 中的过滤参数。
- 后端仍应做最终校验。

避免方式：

- 不要为了“下拉数据更全”去掉 saleStatus/sourceType。

## 10. 折扣比例是实际收取比例，不是优惠比例

现象：

- 录入 `80` 后有人以为是优惠 80%，实际系统按 8 折计算。

根因：

- `discountRate` 的语义是“按总额的多少百分比收取”。
- `actualAmount = totalAmount * discountRate / 100`。
- 展示时 `80` 显示为 `8折`。

解决方案：

- 继续按当前语义处理。
- 如果产品要改成“减免比例”，必须迁移历史数据和后端计算规则，不能只改前端文案。

避免方式：

- 开发收费单相关功能前先确认金额字段含义：
  - `totalAmount` 应收
  - `discountRate` 收取比例
  - `discountAmount` 折扣金额
  - `actualAmount` 实收/应实收
  - `paidAmount` 已收
  - `refundAmount` 退款

## 11. 支付类型不是数组字段，保存时是逗号字符串

现象：

- 多选支付类型回显失败。
- 保存后后端收到数组导致接口异常。

根因：

- 表单中 `paymentTypeValues` 是数组。
- 后端字段 `paymentTypes` 是逗号分隔字符串。

解决方案：

- 编辑时用 `splitPaymentTypes()` 转数组。
- 提交时用 `paymentTypeValues.join(',')` 转回字符串。
- 展示时用 `selectDictLabels(dict.type.medical_payment_type, value)`。

避免方式：

- 不要直接把 Element UI multiple select 绑定到后端字符串字段。

## 12. 非作废且有收退款金额时必须选择支付类型

现象：

- 收费单保存失败，提示必须选择支付类型。

根因：

- 前端规则：`orderStatus !== '4'` 且 `paidAmount > 0` 或 `refundAmount > 0` 时，支付类型不能为空。
- 这是业务核算和流水统计所需。

解决方案：

- 保留 `validatePaymentTypes()`。
- 作废单可以不选支付类型。

避免方式：

- 不要把支付类型校验只绑定在“已收费”状态，因为部分收费、退款也需要支付类型。

## 13. 患者编辑不能回传 `privacyAuth`

现象：

- 修改患者资料时后端报字段无权限、隐私授权异常，或覆盖了隐私授权状态。

根因：

- 患者详情返回中可能包含 `privacyAuth`，但当前表单不负责维护它。
- 代码在编辑时显式 `delete this.form.privacyAuth`。

解决方案：

- 保留删除逻辑。
- 如果以后做隐私授权功能，应独立接口/独立表单处理。

避免方式：

- 不要把接口返回对象无脑原样 PUT 回去。
- 对敏感字段、只读字段、统计字段都要提交前清理。

## 14. 药品/耗材剩余库存不是普通编辑字段

现象：

- 普通用户编辑药品名称后，库存被覆盖。
- 新增药品时错误传了 `remainingQuantity`。

根因：

- `remainingQuantity` 代表库存结果，只有特定库存权限才能直接改。
- 药品权限是 `medical:medicine:stock`，耗材权限是 `medical:consumable:stock`。
- 无权限或新增时，提交前会删除该字段。

解决方案：

- 保留 `canEditRemaining` 和提交前 `delete this.form.remainingQuantity`。
- 新增库存调整功能时应单独设计入库/盘点/调整接口。

避免方式：

- 不要把库存字段当作普通资料字段。
- 不要在共享表单里默认总是展示剩余数量。

## 15. 医院 owner 不能在用户列表被编辑、授权、删除

现象：

- 医院超级管理员被删或降权后，医院无人可管理。

根因：

- 医院 owner 是当前医院最高权限主体。
- 前端用 `isAdmin === '1' || roleLevel === 0` 禁用修改、角色、删除。

解决方案：

- 保留医院用户列表的 owner 禁用逻辑。
- owner 转让只能走个人中心“更换超级管理员手机号”流程，并且成功后强制登出。

避免方式：

- 不要为了“管理员也应该能改所有人”放开 owner 操作。

## 16. 系统超管和医院超管不是同一个概念

现象：

- 系统工具错误展示给医院管理员。
- 医院通知错误展示给系统超管。
- 医院资料编辑权限判断混乱。

根因：

- 系统超管：`roles.includes('admin')` 或 `permissions.includes('*:*:*')`。
- 医院超管：当前医院用户 `isAdmin === '1'`。

解决方案：

- 系统工具、布局设置等按系统权限判断。
- 医院资料、邀请码、医院通知、owner 转让按当前医院身份判断。

避免方式：

- 写权限判断前先问：这是平台系统权限，还是当前医院内权限？

## 17. 注册邀请码和医院创建是互斥路径

现象：

- 用户带邀请码注册时还提交了医院名称，后端归属混乱。

根因：

- 有邀请码表示加入已有医院。
- 无邀请码表示创建/绑定新的医院主体。

解决方案：

- 历史基线保留注册提交前：
  - 手机注册清空 email。
  - 邮箱方式会清空手机号。
  - 有 inviteCode 时清空 hospitalName、hospitalType。
- 2026-06-27 手机号化需求要求移除邮箱注册和邮箱登录入口后，仍需保留“有 inviteCode 时清空 hospitalName、hospitalType”的互斥规则，并确保邮箱字段不提交。

避免方式：

- 不要把所有注册字段都无脑提交。

## 18. 通用医疗类型弹窗目前主要是删除，不是完整 CRUD

现象：

- 打开“病历类型/药品类型”弹窗，只看到标签和删除，没有新增输入框。

根因：

- `TypeManageDialog` 当前逻辑是加载 options，关闭标签加入待删除列表，保存后批量删除。
- 新类型可能通过业务表单 autocomplete 输入并由后端保存时处理。

解决方案：

- 不要误以为弹窗遗漏新增功能而随手补半套前端新增。
- 如果要做完整类型管理，需要和后端确认新增、编辑、被引用校验、排序等接口。

避免方式：

- 类型管理改动前先读 `src/views/medical/components/TypeManageDialog.vue` 和 `src/api/medical/type.js`。

## 19. options 接口返回结构不统一

现象：

- 下拉无数据，但接口返回了。
- 代码只读 `response.data`，实际接口返回 `rows`。

根因：

- 项目中后端接口有若依分页结构，也有 options 结构。
- 现有代码经常写 `response.data || response.rows || []`。

解决方案：

- 新页面参考同类 API 的返回结构。
- 对 options 做兼容读取，特别是医院部门、角色、字典、业务 options。

避免方式：

- 不要默认所有列表都是 `rows`，也不要默认所有下拉都是 `data`。

## 20. request 的 GET 参数会被手动拼接

现象：

- GET 参数被编码成 `params%5BbeginTime%5D` 风格。
- 后端收不到数组或深层对象。

根因：

- `src/utils/request.js` 会把 GET `params` 通过 `tansParams()` 拼到 URL，并清空 `config.params`。
- 该逻辑适配若依后端的 `params[beginTime]`/`params[endTime]`。

解决方案：

- 时间范围继续放在 `queryParams.params`，使用现有工具。
- 复杂数组/深层对象不要直接塞进 GET params，需和后端约定格式。

避免方式：

- 不要在 API 层自己手工拼 URL 后又传 params。

## 21. POST/PUT 默认 1 秒重复提交拦截

现象：

- 连续点保存或连续发相同请求，第二次报“数据正在处理，请勿重复提交”。

根因：

- request 拦截器对同 URL、同数据、1 秒内的 POST/PUT 做拦截。
- 登录接口通过 `headers.repeatSubmit = false` 关闭该逻辑。

解决方案：

- 普通保存保持默认拦截。
- 确实允许快速重复提交的接口，明确设置 `headers: { repeatSubmit: false }`。

避免方式：

- 不要在页面层吞掉该错误后继续重复提交。
- 不要全局关掉重复提交。

## 22. 不要直接 axios 请求绕过全局 request

现象：

- 接口没带 token。
- 401 不弹重新登录。
- 文件下载错误无法解析。
- 重复提交逻辑失效。

根因：

- token、baseURL、错误处理、下载、重复提交都封装在 `src/utils/request.js`。

解决方案：

- 所有业务 API 放入 `src/api/**` 并使用 request。
- 文件下载优先使用全局 `download()` 或插件里现有模式。

避免方式：

- 只有非常特殊的第三方外链请求才考虑单独 axios/fetch，并在代码里说明原因。

## 23. 路由 name 改动会影响缓存

现象：

- tagsView/keep-alive 缓存异常。
- 页面切换后状态丢失或错误复用。

根因：

- 若依模板依赖路由 `name` 和组件 `name` 做缓存。
- `AppMain` 使用 keep-alive include `cachedViews`。

解决方案：

- 新页面组件 `name` 要唯一。
- 不要随意改已有组件 name 或后端菜单 route name。

避免方式：

- 重构文件名和组件名时，把 tagsView、后端菜单、缓存行为一起验证。

## 24. PowerShell 输出乱码不等于文件乱码

现象：

- README 或源码中文注释在终端显示乱码。

根因：

- 文件本身是 UTF-8，但 PowerShell 默认输出编码可能不匹配。

解决方案：

- 使用 `Get-Content -Encoding UTF8 <file>` 查看。

避免方式：

- 不要因为终端乱码去批量改编码或重写中文。

## 25. 没有测试脚本，不能用“测试通过”糊弄

现象：

- `npm test` 或 lint 不存在。
- 修改核心业务后只看编译成功就上线，运行时才暴露问题。

根因：

- `package.json` 只有 `dev`、`build:prod`、`build:stage`、`preview`。
- 项目验证高度依赖手工联调。

解决方案：

- 至少跑 `npm run build:prod`。
- 涉及医疗主链时手工验证：
  - 登录/选择医院
  - 切换医院
  - 后端菜单加载
  - 预约转病历
  - 病历保存/提交
  - 收费明细新增/编辑
  - 收费单金额/支付类型/退款
  - 报表或库存相关展示

避免方式：

- 最终说明里如未运行构建或未手工验证，必须明确说出来。

## 26. 未按 AGENTS 使用 worktree，污染主工作区

现象：

- 新需求刚开始整理需求文档、设计或测试用例时，直接在主工作区创建需求分支。
- 需求文档、设计文档、测试文档、任务拆分或功能代码直接落在主工作区。
- 后续补救时需要迁移改动、恢复主工作区，增加冲突和误改风险。

根因：

- 没有在开始需求前先阅读 AGENTS，也没有枚举并阅读或检索 `docs/project/` 下所有文档文件。
- 没有执行“先确认当前路径是否为需求 worktree”的动作。
- 前后端双仓协同时，只盯着当前仓库，忽略同名需求分支和 worktree 要求。

解决方案：

- 需求文档、开发设计、测试用例、任务拆分或功能开发开始前，先检查当前路径和分支。
- 需求文档、开发设计、测试用例、任务拆分或功能开发开始前，先枚举并阅读或检索 `docs/project/` 下所有文档文件。
- 如果当前路径是主工作区，先创建或切换到需求 worktree，再开展需求相关工作。
- 同一需求涉及 `dhs-core` 和 `dhs-ui` 时，两边使用同名需求主分支，并在各自 worktree 下维护改动。
- 如果已经误在主工作区改动，立即停止继续开发，把改动迁移到需求 worktree，恢复主工作区干净后再继续。
- 完成补救后同时检查主工作区和 worktree 的 `git status --short --branch`。

避免方式：

- 开发前确认当前目录是否是 `worktrees` 下的需求工作区。
- 开发前确认已经枚举并阅读或检索 `docs/project/` 下所有文档文件。
- 开发前确认当前分支是否是本需求主分支或子任务分支。
- 跨仓需求确认 `dhs-core` 和 `dhs-ui` 的需求分支名称一致。
- 主工作区必须保持干净。

## 27. 未基于已实现页面迭代，重复设计入口

现象：

- 现有页面已经在修改弹窗里支持维护某个字段，设计文档又新增一个独立操作按钮。
- 线框只根据字段名或表层理解画页面，没有对照当前系统真实交互。
- 后续开发按错误设计新增重复入口，造成页面复杂、权限分散和用户困惑。

根因：

- 需求整理时只看 PRD 和截图，没有打开现有页面代码或当前系统效果核对。
- 把“业务能力需要保留”误理解为“需要新增一个操作入口”。

解决方案：

- 设计 UI 前先查看现有页面实现、已有弹窗字段和已实现交互。
- 能在现有弹窗字段内迭代的，不新增同类独立按钮。
- 如果现有代码已经同时存在重复入口，例如医院用户页面的“角色/分配医院角色”按钮和修改弹窗里的角色字段，设计必须明确收敛到哪个入口，并写清楚要移除的旧入口。
- 需求只限制弹窗选择后的带出字段时，不要扩展成列表列删除；例如排班弹窗不带出部门、岗位，不代表排班列表要删除部门、岗位列。
- 测试和 UI 状态说明不能写“或”“按设计”等未定分支；需要在设计阶段选定唯一行为。
- 如果确实要改变既有入口，必须在设计中写清楚“替换旧入口”还是“新增入口”，并说明原因。

避免方式：

- 开发前确认这项能力在当前系统是否已经存在。
- 画线框前先列出现有入口和本次变化点。
- 对医院用户这类页面，角色维护以修改弹窗里的角色字段为准；现有独立“角色/分配医院角色”入口应作为重复入口移除。
- 对排班这类页面，区分“弹窗选择员工后带出字段”和“列表已有展示列”，不能把二者混为一谈。
- 对角色管理页面，默认可见角色不是角色层级；系统菜单选择的是 `hospital_id=0` 的默认角色。角色列表不展示默认列，编辑弹窗中角色名称和角色层级置灰。

## 28. 排班日期范围和营业时间确认不能只改表单字段

现象：

- 排班弹窗改成日期范围后，只提交前端展示字段，后端无法按日期生成单日排班。
- 超出营业时间时只在前端提示，不重提交确认标记，导致后端仍拒绝保存或无法标记 `out_of_business_hours`。
- 员工下拉为了辅助识别又拼接部门、岗位、角色，和 6.27 需求冲突。

根因：

- 排班范围保存依赖后端约定的 `scheduleBeginDate`、`scheduleEndDate` 和 `businessHoursConfirmed` 字段，不是把原 `scheduleDate` 换成数组即可。
- 营业时间校验必须由后端结合当前医院规则兜底，前端只能根据后端业务异常做二次确认。
- 手机号需要单独只读展示；部门、岗位只是列表关联展示，不属于弹窗选人后的带出字段。

解决方案：

- 构造排班保存 payload 时，从日期范围拆出 `scheduleBeginDate`、`scheduleEndDate`，并保留 `scheduleDate` 兼容单日回显。
- 首次保存不带 `businessHoursConfirmed`；捕获后端“营业时间/超出营业/休息日”类错误后弹确认，用户继续时带 `businessHoursConfirmed=true` 重提。
- 员工下拉的 label 只使用姓名，手机号放独立 disabled 输入框，提交前删除 `phonenumber` 等纯展示字段。
- 列表继续展示部门、岗位，并新增手机号和超营业时间标记。

避免方式：

- 排班页面改动前先核对 `docs/ui/dhs-medical-ui-20260627.html` 的排班线框和 `dhs-core` 设计文档中的排班字段约定。
- 不要把“弹窗不回填部门/岗位/角色”扩大成“列表删除部门/岗位列”。
- 不要只做前端本地营业时间判断，最终能否保存和标记必须以后端响应为准。
